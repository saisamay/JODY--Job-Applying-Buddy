# Private job trust review

Gmail and manual intake use the same local trust assessment after eligibility screening. Job Discovery shows the two decisions separately. Reviewers can inspect each signal, its severity, explanation and source reference. Historical reassessment appends a trust record using retained facts. A missing source payload limits coverage. It does not initiate a mailbox read.

## Scoring and review

Version `trust-1` awards 30 points for an independently established employer/domain mapping, 10 for an aligned HTTPS posting URL, 40 for independent corroboration of the exact official vacancy, 10 for an aligned recruiter address and 10 for an authorized Gmail platform posting identifier. Recruiter address alignment does not authenticate the sender. Scores are clamped to 0–100. The configured threshold defaults to 80. Coverage measures five groups equally: employer identity, exact vacancy, registry, recruiter and posting source. Confidence is high for a corroborated vacancy with at least 80% coverage, medium for other corroborated vacancies and low otherwise.

Unknown facts earn zero. Public webmail and registration under 180 days each subtract four. Recruiter mismatch, off-platform pressure and evaluator-directed instructions each subtract 15. Unusual urgency subtracts five. Unsafe URLs and conflicting company-domain claims subtract 20. Lookalike hostnames subtract 30. Recruitment payment or sensitive financial requests subtract 45 each. A high or critical finding, blocklist match, conflicting evidence or exceeded 100-sighting window prevents approval regardless of score. These rules detect indicators and can miss unfamiliar wording.

An adequately supported vacancy meets the threshold or receives explicit owner approval for a contextual exception. Approval requires the current assessment, exact official posting URL and a note recording what the owner independently checked. Skip, block and confirmed scam are distinct decisions. The latter two are sticky. Use the existing Settings blocklist separately for company-wide or domain-wide exclusions. No mailbox change, submission or dispatch is part of any review. Preparation also requires eligibility and qualification evidence. A skills-only eligibility question can be resolved by a verified qualification comparison with all mandatory skills matched.

## Operator policy and optional checks

- Configure `JODY_TRUST_EMPLOYERS` on the backend as a JSON object mapping lowercase company names to independently established official DNS domains. Default is empty. Job text cannot add an entry.
- Leave `JODY_TRUST_PUBLIC_CHECKS=0` for offline operation. To run a public check, the operator must first enable the policy and the authenticated owner must explicitly POST the `verify` action to `/api/v1/workspace/jobs/{job_id}/trust` with an idempotency key. The local worker never requests it. Hosted preview locks are respected.
- Each authorization permits one exact HTTPS vacancy page and, for a supported .com domain, one registry request. Only matching JobPosting structured data for the employer, title and exact URL corroborates the vacancy. Other content types, redirect responses and unsupported registries yield unknown. TLS uses the validated public IP and original hostname. Requests carry no owner credentials. Per-tenant limit is three verification attempts/hour. Unchanged checks cache for 24 hours and material changes invalidate corroboration. Each response is bounded to 512,000 bytes.
- For offline reassessment use Job Discovery or the existing local `apps/worker/evaluate_jobs.py` entry point. It handles at most 25 due canonical jobs per invocation. Resume after a pause or restart by invoking it again. Preparation checks current evidence, exclusions and threshold again. The assessment history and audit are tenant-scoped. Public verification has only been tested with synthetic transport responses.
