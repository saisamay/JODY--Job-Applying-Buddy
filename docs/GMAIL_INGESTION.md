# Gmail intake and verification

A private session sets exact authorized senders and optionally a Gmail label ID and subject phrase. A first run captures the profile history watermark before listing bounded recent messages. Later runs read message-added and label-added history and intersect changed IDs with paginated, sender-filtered search results before fetching bodies. This can page through older matching **identifiers** on busy accounts. An expired history watermark restarts bounded discovery. Activity outside the recovery window can be lost. [Google synchronization](https://developers.google.com/workspace/gmail/api/guides/sync) · [History API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list)

PostgreSQL stores the encrypted grant, account state, per-run work list, retry time, counts, processed message references and job evidence. Per-user advisory locks serialize changes. Each message's receipt, canonical job, evidence and work-list advancement share a transaction. The mailbox watermark advances after pending pages and messages commit. The worker checks the global gate and tenant on each unit. Redis loss cannot lose pending intake. The manual button performs up to six units per press. Use **Continue sync** until completion. A sleeping or stopped host makes no progress.

Multipart and HTML parsing ignores attachments and scripts. Exact sender matching and an aligned Gmail DMARC result gate extraction. Forwarded messages and senders with incomplete authentication may require review. Classification distinguishes promotional material, recruitment replies, alerts, direct openings, campus opportunities, suspicious messages, irrelevant mail and uncertain results. Labeled fields and role headings support multiple cards. Heuristics can miss or mis-segment unfamiliar layouts. Stable vacancy links and source requisition IDs support cross-message deduplication. Ambiguous identifiers remain separate. Extracted fields are source claims. Legitimacy assessment remains separate.

Canonical jobs retain only extracted job fields, source domain, discovery date and evidence references. Private mailbox addresses, filters, run counts and message identifiers stay tenant-scoped under RLS. Raw MIME, attachments and entire emails are never archived. Logs contain aggregate counts and route templates. Disconnect retains previously discovered jobs, receipts and run history. A scheduled retention purge is pending.

## Optional model processing

Dashboard filter saves select deterministic processing. Advanced users may PUT the existing policy plus an ordered `providers` array to authenticated `/api/v1/gmail/policy`. Each listed provider is consent to share the minimized job excerpt for this task, including on fallback. Salutations, quoted lines, links and common contact patterns are removed; snippets can still identify people. Leave the array empty for private-only deterministic handling. Loopback Ollama uses `JODY_CHAT_MODEL` and `JODY_OLLAMA_BASE_URL`. Cloud adapters require tenant vault credentials and an explicitly verified, free-only project and supported model. Only then set `JODY_GMAIL_FREE_PROVIDERS` (comma-separated names), `JODY_GMAIL_GEMINI_MODEL` or `JODY_GMAIL_GROQ_MODEL` on the API. Billing-enabled projects are unsuitable. A model listing alone cannot establish free eligibility.

Ambiguous relevant alerts without parsed rows may use the existing tenant encrypted inference cache and daily budget (`JODY_AI_DAILY_CALLS`). Model output must validate and each emitted field must occur in the supplied excerpt. Model-assisted jobs always require review. There are no model tools. Failed authorized routes can fall through only to other listed providers. Rate limits and temporary failures persist retry time with exponential delay and jitter; four consecutive failed attempts terminate the run. Start another run after correcting the issue. The default minimum interval between new runs is 30 seconds (`JODY_GMAIL_MIN_INTERVAL`). Exact AI attempts are in career_usage; aggregate route selections can include cache hits.

## Verification and rollback

- For synthetic tests load the **local** .env, activate .venv, export PYTHONPATH=apps/api and run `pytest`. The suite creates a uniquely named test database, upgrades a legacy fixture, verifies schema drift and rollback/re-upgrade, and removes it. The browser test exercises the normal signed-in shell at five widths. Real cloud inference and Google consent are separate checks.
- Migration `0005_gmail` adds four RLS-protected tables and restricted grants. Existing job and session data remain compatible. To roll back a populated environment, stop readers, back up the database and encryption key, and revert application code first. A downgrade to `0004_career` deletes Gmail credentials and provenance. Prefer keeping additive tables and restoring forward. Never run a destructive downgrade on live data without a separate recovery decision.
- For a local worker, run `PYTHONPATH=apps/api .venv/bin/python apps/worker/gmail_once.py` with the restricted DB credentials, encryption key and Google web client. It drains existing due work. Passing `--schedule` explicitly requests a read. `JODY_GMAIL_WORK_UNITS` bounds this worker invocation (default six, maximum thirty). No timer is installed or hosted worker provisioned.

## Owner-authorized shadow run

1. Complete local OAuth configuration, use the owner's test account and authorize **specific senders**. Start with one sender, three days, five messages and no AI providers. Save the policy. The upper limit is seven days and 25 messages.
2. Only after explicit authorization of that mailbox read, select Sync now, then Continue sync until succeeded. Inspect Job discovery for title, source, date, missing fields and review status. Keep real bodies, addresses and screenshots private.
3. Record aggregate examined, relevant, extracted, stored, duplicates, review and failures. Wait for the minimum interval and repeat with the same policy. On an unchanged mailbox the second run should store zero jobs.
4. Pause again or disconnect. No mailbox write, application or external message is part of this test. Hosting this phase requires separate migration approval, a reviewed HTTPS callback, private configuration and an explicit change to the hosted automation lock.
