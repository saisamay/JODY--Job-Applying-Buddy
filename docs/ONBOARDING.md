# Identity, ownership and onboarding

## What runs today

`POST /api/v1/session` accepts one operator key for the pre-provisioned owner. There is no public signup. Sessions expire, store token digests, and can be revoked. The web cookie is HttpOnly, Secure in production and SameSite=Strict. Protected routes resolve identity on the backend. The new `GET /api/v1/session` returns only the authenticated user ID for read checks. The DB runtime login lacks bypass-RLS, and tenant transactions set a transaction-local user ID. The private probe worker now takes an explicit tenant ID. Its private-only entrypoint supplies the fixed private operator; a public scheduler must replace that binding before dispatch for other users.

Candidates already have versioned, encrypted private fields, multiple resumes, evidence origins, preferences, and resumable step state. The eight steps are basic profile, education/work, skills/projects, GitHub/portfolio, resume upload, job preferences, automation permissions and final confirmation. Optional sections can be deferred. Required fields that are absent or contradictory become questions before use. New profiles are empty of personal claims. Existing owner's portfolio, education, role preferences, repository or contact details never seed other accounts. Treat verified claims, user-provided claims and inferred suggestions separately.

## Future registration gate

1. Select a supported, budget-compatible OIDC identity provider with email verification, recovery and MFA support. Neon Auth stays off. Keep private-owner auth independent and public registration disabled. Use Authorization Code + PKCE, state and nonce, issuer and audience validation, current signing keys and a fixed callback origin. Establish a unique `issuer + subject` mapping. An email match alone never merges accounts.
2. Provision the verified subject exactly once in a transaction with blank candidate profile, settings, paused automation and onboarding rows. Reject an unverified email, disabled identity or replay. Rate-limit enrollment, login, recovery and verification. Give uniform recovery responses and invalidate old sessions after recovery, deletion or operator suspension.
3. Resume the existing onboarding revision on any device. Require explicit per-user consent for sources, hosted AI data classes and external actions. A stored credential grants no authorization by itself. Separate proof of repository/mailbox/chat ownership from a profile claim. Reauthenticate for new sensitive grants, identity changes and deletion.
4. Use a verified session for API commands; obtain user IDs for queued operations only from committed authorized records. Start a scoped DB transaction before reading jobs, prompts, answers, embeddings, caches, resumes or credentials. Queue references carry user and record IDs; claim via tenant filter and locks. Check active identity, scopes, credential revision, quotas, pause and approval again at execution and at dispatch. MCP grants have narrow operations, owner, expiry and revocation. Never trust a tenant ID in a callback or model output.
5. Offer per-provider disconnect: revoke provider grant where supported, delete local ciphertext, invalidate connection receipts/cursors and cancel pending work. The current local vault removal deletes the secret and audits the action; owner must independently revoke current provider credentials. For account deletion require reauthentication and explicit confirmation. Disable jobs and sessions immediately, revoke grants, delete files/versions/evidence and tenant records, redact retained audit metadata, document backup expiry, and prevent restore from resurrecting deleted accounts. Public registration, recovery and full erasure UI are planned.

## Release evidence before a second real user

Use two synthetic users, swapped tokens/resource IDs and concurrent transactions. Cover onboarding/candidate changes, resume download, integration rows, read-model cards, portfolios, embeddings, quota counters, blocked domains, audit, answers and durable tasks. Race signup and duplicate callback, expired/replayed Telegram link, swapped browser state, session logout during OAuth, replaced credential during verify, disconnect during dispatch, kill switch and account deletion during processing. Reuse one pooled connection sequentially for A, B and no tenant. Every negative case must return no data or perform no mutation. Simulate recovery email abuse and enumeration, withdrawn consent, deleted user's backups restored, and fairness under a saturated tenant queue. Require these tests, independent identity-provider setup and an explicit release decision before opening registration. [Existing isolation suite](../tests/test_secure_data.py)
