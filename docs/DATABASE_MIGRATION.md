# Render → Neon migration decision and rehearsal

**Decision on 25 November 2026:** keep the existing Render database, Vercel project and Render API in place. The owner created a Neon Free project with Neon Auth off. No Neon credential or branch was verified by JODY. No hosted dump, restore, cutover, destructive DDL or new resource was authorized in this phase.

## Current evidence

- The production checkpoint uses PostgreSQL 16, Alembic `0004_career` and pgvector. Render readiness returned PostgreSQL and Redis true. Render's read-only connector could not inspect the database because its external IP allowlist is empty. Keep it closed. Direct production table counts, vector version, role metadata and actual data volume still require an authorized operator inside the private network.
- Local inventory returned PostgreSQL 16.15, vector 0.8.7 and the same revision. Of 31 ordinary public tables, the 30 application tables have RLS enabled; the remaining table is `alembic_version`. The runtime role checks active RLS at startup and a transaction-local tenant scope protects subsequent queries. Security-definer lookups and the global dispatch gate have specific grants.
- [Restore regression](../tests/test_restore.py) runs a real PostgreSQL 16 custom-format dump of an isolated migrated fixture with a synthetic encrypted canary. It streams the archive into GnuPG, decrypts into `pg_restore --single-transaction` on a separate unique database, upgrades to head and reapplies restricted grants. It compares every application table count, checks pgvector, verifies PUBLIC cannot execute the session lookup, decrypts using the original key and denies another tenant access. Restoring without ACLs resets function privileges; the provisioner now revokes PUBLIC explicitly. Source database, decryption key and operating-system passphrase in this test are disposable.
- PostgreSQL is authoritative for jobs and the retry outbox. Redis transports task references. Rebuild pending work from PostgreSQL after a loss; do not transfer a Redis list as the authoritative queue.

## Gates before a migration can be approved

1. **Capacity and compatibility.** Inspect Neon Console → project usage and branch settings. The published Free plan currently lists 100 CU-hours/project/month, 5 GB public transfer/project/month and five-minute idle suspension. Verify current storage allocation in the console and allow space for indexes, vectors, encrypted PDFs and restore history. At 0.25 CU, constant activity for a 30-day month consumes about 180 CU-hours. Continuous polling or external health checks can keep a free database awake. Select PG16 for the first rehearsal and a supported vector extension version. [Neon plans](https://neon.com/docs/introduction/plans) · [pgvector](https://neon.com/docs/extensions/pgvector)
2. **Source inventory.** Use a direct admin connection from a trusted private runtime with an approved export path. Record database size, logical row counts per table, indexes, constraints, sequences, extensions, Alembic head, RLS policies, role privileges/memberships and security-definer ownership/search paths. Keep tenant content, email and connection strings out of logs. Compare write rates to the maintenance window. Account for sessions, approvals, encrypted artifacts and idempotency receipts.
3. **Separate target.** Use a disposable Neon branch with its own direct TLS URL and restricted role. Check `python -m jody.provider_check neon` using `JODY_NEON_TEST_DATABASE_URL`; this reads catalog availability only. For actual DDL/restore, get the direct host and the correct branch/database from the Console. A Neon Console-created role can inherit elevated managed-role privileges. Create the runtime login with SQL under the migration owner, verify role memberships and exercise the RLS startup check. Never use the console owner to serve user requests.
4. **Encrypted export before writes or switching endpoints.** Run compatible PG16 client binaries, GnuPG and a known backup-recipient public key. On trusted Linux store distinct source/target connection settings as libpq services and secrets in a mode-0600 passfile. Keep the JODY encryption key in a separate secure store. The following examples expect the operator-created service aliases, an empty disposable destination and a fingerprint verified out of band. No credentials go in shell arguments. Check each pipeline's exit status.

   ```bash
   set -euo pipefail
   umask 077
   pg16=/usr/lib/postgresql/16/bin
   "$pg16/pg_dump" --dbname='service=jody_source' --format=custom --no-owner --no-acl |
     gpg --encrypt --recipient "$BACKUP_RECIPIENT_FINGERPRINT" --output jody.dump.gpg
   sha256sum jody.dump.gpg > jody.dump.gpg.sha256
   sha256sum -c jody.dump.gpg.sha256
   gpg --decrypt jody.dump.gpg |
     "$pg16/pg_restore" --dbname='service=jody_rehearsal' --no-owner --no-acl --exit-on-error --single-transaction
   ```

   Store ciphertext and checksum outside the checkout. Record key custodian, timestamp, artifact size and access policy. Rehearse decryption, do not count the existence of a backup file as a restore. A previous local test pairing a PG18 client with a PG16 destination failed on `transaction_timeout`; both sides of the verified rehearsal use PG16 clients.
5. **Verify new DB.** In a separate backend process set rehearsal `DATABASE_URL` and a new `JODY_DB_APP_PASSWORD`. Load the original application encryption key for data readback. Run `alembic upgrade head`, `python -m jody.provision` and `alembic check`. Default direct-url upgrade/provision must have succeeded before serving traffic. Verify constraints, pgvector and similarity queries, indexes, counts, ciphertext digests, a consented canary's cleartext and correct restricted ownership. Confirm RLS for A, B and no tenant and validate revoked sessions. Run the full suite on **separate test fixtures**, not against the rehearsal accounts; run the hosted smoke against a dedicated isolated stack.
6. **Pooling and cold starts.** Start with the direct runtime endpoint. Neon pooled endpoints use transaction pooling; `SET LOCAL` belongs in the same transaction as the protected query. Admin DDL, migrations, role provisioning and backup use direct connections. Test concurrent A/B requests through the same physical connections, aborted transactions, cold starts, connection limits, timeouts, prepared statements and Redis loss. Existing `runtime_engine` sends startup `options`; managed poolers may reject them. Enable a pooled URL only after these checks pass; do not weaken RLS or remove timeouts to make admission succeed. [Neon pooling](https://neon.com/docs/connect/connection-pooling)
7. **Cutover and rollback require a later decision.** Obtain explicit authorization, a maintenance window, operator and recovery targets. Lock automation, stop workers **and all interactive writes**; freeze sessions or put the API in maintenance. Take a final encrypted export, replay validated restore, compare counts/cursors/receipts and decrypt again. Stage a new API revision/config first; the present Docker entrypoint derives a restricted role from its admin DSN on startup and the Blueprint still binds `DATABASE_URL` to Render. Review an explicit Blueprint/config change before switching. Keep source read-only and rollback secrets available. Reopen writes only after login, resume, policy, audit, queue and isolated tenant checks pass. Before new writes, rollback points the API back to Render. After new writes, freeze both sides and reconcile the delta from immutable IDs/receipts or restore forward; a blind DSN swap loses data. No automatic deletion or plan upgrade.
