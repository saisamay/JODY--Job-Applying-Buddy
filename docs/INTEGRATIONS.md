## Integrations screen and states

The authenticated Integrations view lists purpose, current state and setup instruction for each provider. The backend projects the current session's records through RLS. Stored credential bytes, identifiers of another tenant and bot tokens never appear in a card. The server holds the preview lock. The existing isolated UI design and public routes stay intact.

| Contract state | Entry evidence | Allowed next action |
|---|---|---|
| Disconnected | No live grant or credential | Show requirements and start opt-in setup. |
| Authorization required | Credential entered without proof, or missing consent/scope | Show scope and initiate authorization. Key presence alone cannot produce a verified badge. |
| Connecting | Future durable, expiring owner-bound attempt is in progress | Show attempt time, allow cancellation, suppress duplicate submissions. |
| Connected and verified | Successful identity/capability probe for precisely this tenant, credential revision, scope and target | Show verified time, granted capability, verification and disconnect actions. |
| Expired | Provider confirms invalid/expired grant or recorded expiry passes | Stop queued work, require reauthorization. |
| Failed | Bounded probe failed or policy changed | Redacted reason, retry only when safe; retain last success separately. |
| Disabled | Preview lock, provider restriction, missing implementation or owner disable | Explain gate; prevent pairing, dispatch and background reads. |

Seven states are typed in the shared API. The current screen projects disconnected, authorization required and disabled. Operator preflight is separate from the user connection lifecycle. Prompts 6–14 must persist attempts/evidence before enabling the other states. Persist `user_id, provider, target, credential_revision, granted_scopes, verified_at, expires_at, last_error_class`. Replace, revoke or target change invalidates verification immediately. Lock or compare-and-swap on revision on completion; a stale successful probe cannot revive a removed grant.

## Adapter boundaries

- **Gmail.** Owner preflight exercises authorization code + S256 PKCE, browser nonce, exact redirect, five-minute single-use state, offline refresh and `users.me.getProfile`. The probe discards tokens. Tenant linking will require a session-bound expiring transaction, atomic consumption, encrypted refresh-token storage, handling refresh rotation/revocation and a verified receipt. Gmail alert discovery must parse all jobs in an authorized alert, retain message/thread IDs and commit a per-user cursor with dedupe. Use incremental consent for send separately; modify and destructive actions require separate gates. [Setup and callback URLs](SECRETS_CHECKLIST.md#3-gmail-oauth)
- **GitHub and master resume.** Selected-repository Contents read PAT works for metadata and pinned-file preflight. GitHub App installations with explicit repository selection are a future multi-user alternative. Record repository ID, commit and path; verify membership on every refresh. Preserve original bytes. PDF uploads and PDF/DOCX/TeX career snapshots already exist. LaTeX ZIP import is planned: bound compressed and expanded size, count and compile time, reject traversal, absolute paths, symlinks and nested archives, select the main TeX file, run isolated Tectonic with a pinned offline bundle. Each derived PDF has its own digest and version. Source material still needs claim review. No paid Overleaf dependency.
- **Telegram.** One application bot token lives on the backend. Future user starts linking while signed in. Generate a high-entropy opaque code, store only its digest, user, bot, expiry (five minutes) and used time. Accept it only in a private chat via authenticated webhook or a single authorized poller. Atomically consume and bind the numeric chat and sender to one user. Replays, expired codes, groups and conflicting bindings fail closed. For replies verify webhook secret, dedupe update ID, chat + sender match, live user/session policy, pending notification/action ID, expiry and current resource owner. Recheck authorization on dispatch. Disconnect invalidates binding and pending reply actions. A chat ID supplied by the browser is never proof. Test swapped chats, duplicate updates and reassignment before enabling notifications.
- **LinkedIn.** Plan automatic discovery through consented LinkedIn job-alert emails or an explicitly licensed feed. A feed reader may be passive and still prohibited. No session scraping, browser extension harvesting, auto-connect, auto-DM or Easy Apply automation. For restricted portals prepare a reviewed packet and handoff. [LinkedIn terms](https://www.linkedin.com/legal/user-agreement)
- **WhatsApp.** Optional linked-device adapter is disabled. Before an implementation, require documented platform authorization for the use case, tenant opt-in, and explicit separate risk acknowledgement for the unofficial client. Acknowledgement alone cannot authorize prohibited collection. Design a short-lived QR visible only to the initiating signed-in user, one-use pairing nonce and encrypted tenant/device session, with reconnect/unpair and remote-device revocation. Discard non-allowlisted group/channel events before logging, storing media, embedding or queueing. Read-only capability set has no send operation. Test expiry, disconnect, kill switch and cross-user group/session swaps using fixtures. No real QR or session was generated. [WhatsApp terms](https://www.whatsapp.com/legal/terms-of-service)
- **Notifications.** A durable private dashboard inbox is the planned source of truth. Enqueue Telegram primary, separately authorized Gmail fallback, optional ACL-protected ntfy; dedupe each delivery per user/event/channel. Cover shortlist, assessment, interview, offer, missing answer, risk review, disconnection, worker failure and daily digest. External text contains an event category and a sign-in link; private questions, resume content and company correspondence remain behind authentication. Unknown receipt pauses reconciliation rather than retrying blind. Local state, delivered receipt, approved reply and resulting decision are distinct records.
